# Objects/complexobject.c

<CpyLink path="Objects/complexobject.c" />

`complexobject.c` defines CPython's `complex` built-in type. The core representation is a plain C struct, `Py_complex`, containing two `double` fields named `real` and `imag`. All arithmetic operates directly on these structs before any Python object is allocated, keeping reference counting out of the hot path. The file exports both the C API (`PyComplex_New`, `PyComplex_RealAsDouble`, `PyComplex_ImagAsDouble`) and the full `PyNumberMethods` slot table that drives Python-level operations.

### Pure-C arithmetic layer (`_Py_c_sum` through `_Py_c_pow`)

```c
// CPython: Objects/complexobject.c:41 _Py_c_sum
Py_complex
_Py_c_sum(Py_complex a, Py_complex b)
{
    Py_complex r;
    r.real = a.real + b.real;
    r.imag = a.imag + b.imag;
    return r;
}
```

The four basic operations (`_Py_c_sum`, `_Py_c_diff`, `_Py_c_prod`, `_Py_c_quot`) accept and return bare `Py_complex` structs with no Python object involvement. `_Py_c_quot` uses a two-branch algorithm to avoid catastrophic cancellation when one component dominates:

```c
// CPython: Objects/complexobject.c:85 _Py_c_quot
Py_complex
_Py_c_quot(Py_complex a, Py_complex b)
{
    Py_complex r;
    double abs_breal = b.real < 0 ? -b.real : b.real;
    double abs_bimag = b.imag < 0 ? -b.imag : b.imag;
    if (abs_breal >= abs_bimag) {
        double ratio = b.imag / b.real;
        double denom = b.real + b.imag * ratio;
        r.real = (a.real + a.imag * ratio) / denom;
        r.imag = (a.imag - a.real * ratio) / denom;
    } else {
        double ratio = b.real / b.imag;
        double denom = b.real * ratio + b.imag;
        r.real = (a.real * ratio + a.imag) / denom;
        r.imag = (a.imag * ratio - a.real) / denom;
    }
    return r;
}
```

`_Py_c_pow` special-cases zero exponents and integral exponents before falling back to `cexp(log(z) * w)` for the general case.

### Coercion and the `__complex__` protocol

```c
// CPython: Objects/complexobject.c:361 PyComplex_AsCComplex
Py_complex
PyComplex_AsCComplex(PyObject *op)
{
    Py_complex cv;
    PyObject *newop = NULL;

    /* Fast path: already a complex */
    if (PyComplex_Check(op)) {
        return ((PyComplexObject *)op)->cval;
    }
    /* Try __complex__ */
    newop = _PyObject_CallMethod(op, &_Py_ID(__complex__), NULL);
    if (newop == NULL) { cv.real = -1.; return cv; }
    if (!PyComplex_Check(newop)) {
        PyErr_SetString(PyExc_TypeError,
                        "__complex__ should return a complex object");
        Py_DECREF(newop);
        cv.real = -1.;
        return cv;
    }
    cv = ((PyComplexObject *)newop)->cval;
    Py_DECREF(newop);
    return cv;
}
```

This is the mechanism that lets user-defined classes integrate with `complex()` and with arithmetic operators. `PyComplex_RealAsDouble` and `PyComplex_ImagAsDouble` both call through `PyComplex_AsCComplex`, so any object with `__complex__` automatically satisfies both accessors.

### `complex_new` and argument parsing

```c
// CPython: Objects/complexobject.c:981 complex_new
static PyObject *
complex_new_impl(PyTypeObject *type, PyObject *r, PyObject *i)
{
    Py_complex cr, ci;

    /* String argument goes through PyOS_string_to_double parser */
    if (PyUnicode_Check(r)) {
        if (i != Py_None) {
            PyErr_SetString(PyExc_TypeError, ...);
            return NULL;
        }
        return complex_from_string_inner(r, type);
    }

    cr = PyComplex_AsCComplex(r);
    if (cr.real == -1.0 && PyErr_Occurred()) return NULL;

    if (i == Py_None) {
        ci.real = ci.imag = 0.0;
    } else {
        ci = PyComplex_AsCComplex(i);
        if (ci.real == -1.0 && PyErr_Occurred()) return NULL;
    }
    /* complex(a+bj, c+dj) == (a - d) + (b + c)j */
    return PyComplex_FromDoubles(cr.real - ci.imag, cr.imag + ci.real);
}
```

The subtraction of `ci.imag` from the real part is the correct mathematical identity: when the second argument is itself complex, its imaginary part contributes to the real component of the result.

### Hash and equality

`complex_richcompare` only handles `==` and `!=`. Any order comparison raises `TypeError` with a message indicating complex numbers are unordered. The hash follows the numeric tower rule: if the imaginary part is zero, `complex.__hash__` must equal `int.__hash__` for the same real value.

```c
// CPython: Objects/complexobject.c:801 complex_hash
static Py_hash_t
complex_hash(PyComplexObject *v)
{
    Py_uhash_t hashreal = _Py_HashDouble((PyObject *)v, v->cval.real);
    if (hashreal == (Py_uhash_t)-1) return -1;
    Py_uhash_t hashimag = _Py_HashDouble((PyObject *)v, v->cval.imag);
    if (hashimag == (Py_uhash_t)-1) return -1;
    /* Combine real and imag hashes so that hash(x+0j) == hash(x) */
    Py_uhash_t combined = hashreal + _PyHASH_IMAG * hashimag;
    if (combined == (Py_uhash_t)-1)
        combined = (Py_uhash_t)-2;
    return (Py_hash_t)combined;
}
```

## gopy mirror

`complexobject.c` has no counterpart in gopy yet. The natural home for a future port is `objects/complex.go`. The pure-C arithmetic layer maps cleanly to Go functions operating on a `struct{ Real, Imag float64 }`, and Go's `math/cmplx` package provides cross-check primitives. The `__complex__` protocol lookup fits into gopy's existing `protocol.go` pattern. `complex_richcompare` would be straightforward to port since it only needs to handle equality and must raise `TypeError` for ordering, matching the pattern already used in `objects/type.go`.
