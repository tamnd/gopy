# `Python/formatter_unicode.c`

<CpyLink path="Python/formatter_unicode.c" />

Implements the `__format__` slot for the four built-in scalar types:
`str`, `int`, `float`, and `complex`. The file is also the home of the
mini-language parser (`parse_internal_render_format_spec`) that turns a
format spec string such as `">10.3f"` into the `InternalFormatSpec`
struct consumed by each type's formatter.

The public surface is four functions, one per type, each named
`_Py<Type>_FormatAdvancedWriter`. They are called indirectly from
`CONVERT_VALUE` / `FORMAT_VALUE` opcodes via `PyObject_Format`, which
looks up `type.__format__` on the value object. The private helpers
(`format_string_internal`, `format_long_internal`, `format_float_internal`,
`format_complex_internal`) do the actual work; the `…AdvancedWriter` wrappers
handle the zero-length spec fast path and the type dispatch.

The number formatting path is the more complex one. `calc_number_widths`
computes the field layout (sign, prefix, grouped digits, decimal point,
remainder, padding) into a `NumberFieldWidths` struct, and `fill_number`
writes each field into the `_PyUnicodeWriter` in order. Locale-aware
formatting (the `n` type code and thousands separators) is handled by
`get_locale_info` / `free_locale_info`, which query `localeconv()` and
return Python string objects for the decimal point and separator characters.

gopy ports the spec parser and string formatter in `format/format.go` and
wires them to `str.__format__` via `objects/str_format.go:unicodeFormat`.
Integer and float format paths are partially ported; complex formatting is
not yet implemented.

The parser is a one-pass scan that never backtracks. The `[[fill]align]`
prefix requires a two-character lookahead: if the second character is an
alignment token (`<`, `>`, `=`, `^`) then the first is the fill; if
only the first character is an alignment token, no fill character was
specified and the default fill (space) is kept. Each optional field is
tested with a `if (end-pos >= N && ...)` guard so the parser never
reads past the end of the spec. 3.14 adds the `z` flag (negative-zero
coercion for floats) and fractional-part thousands separators (`,`/`_`
after `.precision`).

```c
int
_PyUnicode_FormatAdvancedWriter(_PyUnicodeWriter *writer,
                                PyObject *obj,
                                PyObject *format_spec,
                                Py_ssize_t start, Py_ssize_t end)
{
    InternalFormatSpec format;

    /* zero-length spec: just write str(obj) */
    if (start == end) {
        if (PyUnicode_CheckExact(obj))
            return _PyUnicodeWriter_WriteStr(writer, obj);
        else
            return format_obj(obj, writer);
    }

    if (!parse_internal_render_format_spec(obj, format_spec, start, end,
                                           &format, 's', '<'))
        return -1;

    switch (format.type) {
    case 's':
        return format_string_internal(obj, &format, writer);
    default:
        unknown_presentation_type(format.type, Py_TYPE(obj)->tp_name);
        return -1;
    }
}
```

All four `…FormatAdvancedWriter` functions share the same structure:
fast-path for an empty spec (no parsing needed), parse the spec, and
dispatch to the type-specific internal formatter. They write directly
into a `_PyUnicodeWriter` rather than constructing an intermediate
`PyObject *`, which avoids one allocation per `FORMAT_VALUE` opcode.
The `default_type` and `default_align` arguments to
`parse_internal_render_format_spec` differ per type: strings use `s`
and left-align (`<`); integers use `d` and right-align (`>`); floats
use `\0` (the no-type-code path in `format_float_internal`) and
right-align.
