# `Lib/dis.py`

<CpyLink path="Lib/dis.py" />

`Lib/dis.py` is the Python-level bytecode disassembler. It accepts
almost any Python object (function, class, module, code object, source
string, or raw bytes) and renders the bytecode as a table of mnemonics,
arguments, and resolved values.

The module is structured around a small public API that delegates to a
set of private helpers. `dis` and `disassemble` are the top-level
entry points. `get_instructions` is the structured alternative: it yields
`Instruction` named tuples rather than printing text, which makes it
useful for tools that programmatically inspect bytecode. The inner loop
`_get_instructions_bytes` does the actual decoding work by walking the
raw bytecode array two bytes at a time (each opcode is one byte, each
argument one byte, with `EXTENDED_ARG` for values over 255).

Two additional decoders handle the variable-length tables stored alongside
the bytecode: `findlinestarts` decodes `co_linetable` to map offsets to
line numbers, and `_parse_exception_table` decodes the exception handler
ranges. Both tables use a compact delta-encoded format introduced in
Python 3.12.

gopy's bytecode lives in `compile/`; the disassembler port, when shipped,
will live in `module/dis/module.go` and expose the same `Instruction` API
over gopy's instruction set.

`Instruction` is a named tuple subclass so it is both iterable (useful
for unpacking) and has a readable `_disassemble` method for formatting
output lines. The `starts_line` field is `None` for most instructions and
is set to the line number only on the first instruction of each source
line, which is how the disassembler produces the line-number column
without repeating it on every row. `argrepr` is a human-readable
description of the resolved argument value: for `LOAD_GLOBAL` it is the
name string; for `JUMP_FORWARD` it is the target offset.


The loop calls `_unpack_opargs`, which handles `EXTENDED_ARG` chaining
transparently: each call yields an `(offset, op, arg)` triple where `arg`
already has the extended prefix merged in. From there the function
resolves `argval` through a series of opcode-category checks (constants,
names, locals/cells, jump targets, format specifiers for `FORMAT_VALUE`).
This is the single place in the module where all argument types are
decoded; both `disassemble` and `get_instructions` funnel through it.

### `findlinestarts` and the linetable format (lines 561 to 650)

<CpyLink path="Lib/dis.py" lines="561-650" />

```python
def findlinestarts(code):
    """Find the offsets in a byte code which are start of lines in the source.
    Generate pairs (offset, lineno) as described in Python/compile.c.
    """
    lastline = None
    for start, end, line in code.co_lines():
        if line is not None and line != lastline:
            lastline = line
            yield start, line
```

Python 3.12 replaced the old `co_lnotab` two-byte-pair encoding with a
richer `co_linetable` that also records column offsets and end positions.
`co_lines()` is a C method that iterates the new format and yields
`(start, end, line)` triples. `findlinestarts` filters to the first
offset per source line, preserving the same `(offset, lineno)` interface
that older code expected. Tools that need the full position data (for
precise error highlighting) use `co_positions()` instead, which
`_get_instructions_bytes` uses when building `Instruction.positions`.

### `_parse_exception_table` (lines 731 to 820)

<CpyLink path="Lib/dis.py" lines="731-820" />

```python
def _parse_exception_table(code):
    iterator = _parse_varint(code.co_exceptiontable)
    try:
        while True:
            start = next(iterator) * 2
            length = next(iterator) * 2
            end = start + length - 2
            target = next(iterator) * 2
            dl = next(iterator)
            depth = dl >> 1
            lasti = bool(dl & 1)
            yield _ExceptionTableEntry(start, end, target, depth, lasti)
    except StopIteration:
        return
```

`co_exceptiontable` is a compact byte sequence introduced in Python 3.11
to replace the old block stack. Each entry encodes a bytecode range
(`start` to `end`), the handler target offset, the stack depth at the
entry point, and a `lasti` flag that controls whether the `RESUME` opcode
at the target should restore `f_lasti`. Values are stored as variable-
length integers (`_parse_varint` reads them one byte at a time, using the
high bit as a continuation flag). The `depth` field is used by the
interpreter to pop excess stack entries before jumping to the handler.
