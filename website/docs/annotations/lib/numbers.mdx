# `Lib/numbers.py`

<CpyLink path="Lib/numbers.py" />

`Lib/numbers.py` defines the numeric tower that CPython uses for type
dispatch and `isinstance` guards throughout the standard library. The
tower, introduced by PEP 3141, is a five-level hierarchy of abstract base
classes: `Number`, `Complex`, `Real`, `Rational`, and `Integral`. Each
level is a strict superset of the one below it.

All five classes use `ABCMeta` as their metaclass and mark every method
`@abstractmethod` where a concrete implementation is required. Subclasses
that provide concrete implementations of all required methods automatically
satisfy the ABC without any explicit registration call. Types defined outside
this module (`int`, `float`, `complex`, `fractions.Fraction`,
`decimal.Decimal`) are registered as virtual subclasses, so
`isinstance(3, numbers.Integral)` returns `True` without `int` inheriting
from `numbers.Integral` directly.

The module is deliberately small. Its role is to define the interface
contracts; actual arithmetic lives in `Lib/fractions.py`,
`Lib/decimal.py`, and the C-level numeric types. All `@abstractmethod`
implementations here raise `NotImplementedError` as placeholders; the
concrete `Real` and `Rational` methods provide derived operators from the
required primitives (e.g., `__le__` from `__lt__` and `__eq__`).

### `Number` and `Complex` (lines 31 to 160)

<CpyLink path="Lib/numbers.py" lines="31-160" />

```python
class Number(metaclass=ABCMeta):
    """All numbers inherit from this class.
    If you just want to check if an argument x is a number,
    without caring what kind, use isinstance(x, Number).
    """
    __slots__ = ()
    __hash__ = None

class Complex(Number):
    __slots__ = ()

    @abstractmethod
    def __complex__(self):
        """Return a builtin complex instance."""

    @abstractmethod
    def __abs__(self):
        """Returns the Real distance from 0."""

    @abstractmethod
    def __add__(self, other):
        raise NotImplementedError

    def __ne__(self, other):
        # The default __ne__ in object is fine, but subclasses that
        # define __eq__ must also handle __ne__ correctly.
        return not (self == other)
```

`Number.__hash__ = None` deliberately makes `Number` instances unhashable
unless a subclass provides `__hash__`. This matters because `__eq__` in
`Complex` is abstract; Python's rule is that if a class defines `__eq__`
without defining `__hash__`, `__hash__` is set to `None`. Setting it
explicitly on `Number` makes the intent clear and prevents the default
`object.__hash__` from being accidentally inherited by abstract subclasses.

`Complex.__ne__` is the only non-abstract, non-derived method in the class.
It is provided because Python 3 no longer automatically derives `__ne__` from
`__eq__`, so the ABC needs to supply a consistent default for any concrete
subclass that only implements `__eq__`.

### `Real` — derived methods from primitives (lines 161 to 240)

<CpyLink path="Lib/numbers.py" lines="161-240" />

```python
class Real(Complex):
    __slots__ = ()

    @abstractmethod
    def __float__(self):
        """Any Real can be converted to a native float object."""

    @abstractmethod
    def __trunc__(self):
        """Truncates self to an Integral."""

    @abstractmethod
    def __floor__(self):
        ...

    @abstractmethod
    def __ceil__(self):
        ...

    @abstractmethod
    def __round__(self, ndigits=None):
        ...

    @abstractmethod
    def __lt__(self, other):
        ...

    @abstractmethod
    def __le__(self, other):
        ...

    # Concrete derivations from Complex's abstract methods:
    def __complex__(self):
        return complex(float(self))

    @property
    def real(self):
        return +self

    @property
    def imag(self):
        return 0

    def conjugate(self):
        return +self
```

`Real` fills in `__complex__`, `real`, `imag`, and `conjugate` as concrete
implementations derived from `__float__` and `__pos__`. The `real` property
returns `+self` rather than `self` to ensure that the return type is a new
object rather than the original value (in case `__pos__` performs a type
conversion). A concrete subclass of `Real` needs to implement only the abstract
methods; all derived methods come for free.

The absence of `__gt__` and `__ge__` as abstract methods is deliberate: the
default `object.__gt__` and `object.__ge__` implementations return
`NotImplemented`, which causes Python to try the reflected operation on the
other operand. Combined with `__lt__` and `__le__`, this gives correct
cross-type comparison without extra code.

### `Rational` — concrete `__float__` (lines 241 to 290)

<CpyLink path="Lib/numbers.py" lines="241-290" />

```python
class Rational(Real):
    __slots__ = ()

    @property
    @abstractmethod
    def numerator(self):
        raise NotImplementedError

    @property
    @abstractmethod
    def denominator(self):
        raise NotImplementedError

    def __float__(self):
        """float(self) = self.numerator / self.denominator
        It's important that this conversion use the integer's "true"
        division rather than casting one side to float first.
        """
        return int(self.numerator) / int(self.denominator)
```

The concrete `__float__` uses `int(numerator) / int(denominator)` rather
than `float(numerator) / float(denominator)`. Using `int` division via the `/`
operator means Python picks the best floating-point approximation of the
exact quotient, whereas converting numerator or denominator to `float`
first could lose precision for large integers before the division happens.
This implementation is inherited by `fractions.Fraction` and is the reason
`float(Fraction(1, 3))` gives the same result as `1/3` in Python.

### `Integral` — bit-operation abstracts and concrete derivations (lines 291 to 350)

<CpyLink path="Lib/numbers.py" lines="291-350" />

```python
class Integral(Rational):
    __slots__ = ()

    @abstractmethod
    def __int__(self):
        raise NotImplementedError

    def __index__(self):
        return int(self)

    @abstractmethod
    def __pow__(self, exponent, modulus=None):
        """self ** exponent % modulus, accepting an optional modulus."""
        raise NotImplementedError

    @abstractmethod
    def __lshift__(self, other): raise NotImplementedError
    @abstractmethod
    def __rlshift__(self, other): raise NotImplementedError
    @abstractmethod
    def __rshift__(self, other): raise NotImplementedError
    @abstractmethod
    def __rrshift__(self, other): raise NotImplementedError
    @abstractmethod
    def __and__(self, other): raise NotImplementedError
    # ... __rand__, __xor__, __rxor__, __or__, __ror__, __invert__

    # Concrete derivations:
    def __float__(self):
        return float(int(self))

    @property
    def numerator(self):
        return +self

    @property
    def denominator(self):
        return 1
```

`__index__` is implemented as `int(self)` rather than being left abstract.
The `__index__` protocol is used by CPython whenever an object is used as a
sequence index or slice bound, so any concrete `Integral` subclass that
implements `__int__` automatically gets indexing support. `__pow__` is
declared abstract with a three-argument signature to require that concrete
subclasses handle `pow(x, y, modulus)` natively (the built-in `pow` passes
`modulus` as the third argument). The `numerator`/`denominator` properties
satisfy `Rational`'s abstract requirements; returning `1` for denominator
makes all integer-valued fractions compare equal to their `Fraction` counterparts.
