# `Lib/subprocess.py`

<CpyLink path="Lib/subprocess.py" />

`subprocess` provides the `Popen` class and a handful of convenience
wrappers for launching child processes, wiring up their stdio streams, and
collecting their results. It replaced the older `os.popen`, `os.system`,
and `commands` APIs, and remains the lowest-level process-spawning
interface available in pure Python without dropping into `os.fork` and
`os.execvp` directly.

The file has two large `_execute_child` implementations guarded by
`if mswindows:` / `else:`. The POSIX path uses `os.fork()`, optionally
runs `preexec_fn` in the child, then calls `os.execvpe`. The Windows path
calls `CreateProcess` via the `_winapi` C extension. Both paths share the
same pipe setup logic (`PIPE = -1`, `STDOUT = -2`, `DEVNULL`) and the same
`communicate`/`wait` API above them.

The module also provides `run`, `check_call`, and `check_output` as
high-level one-shot helpers, plus the result and exception types
`CompletedProcess`, `CalledProcessError`, and `TimeoutExpired`.

The constructor resolves all the stdio arguments to file-descriptor pairs
before calling `_execute_child`. `PIPE` causes `os.pipe()` to be called,
giving two ends of a new pipe. `DEVNULL` opens `/dev/null` (or `nul` on
Windows) lazily via `_get_devnull`. `STDOUT` (value `-2`) is only valid
for `stderr` and redirects it to the same fd as stdout. After `_execute_child`
returns, the parent closes the child-side fds (e.g. `p2cread`, `c2pwrite`,
`errwrite`) so that reads on the parent's end of the pipe will see EOF when
the child closes its end.

The actual `fork()` + `exec()` call is in the C extension `_posixsubprocess`
to avoid running any Python code between `fork` and `exec` (which is unsafe
with threads). An error pipe carries any failure from the child: if `preexec_fn`
raises or `execvpe` fails, the child writes `errno` plus a pickle of the
exception to `errpipe_write` before exiting. The parent reads from
`errpipe_read` after `fork_exec` returns and re-raises accordingly.

`pass_fds` is sorted and deduplicated before being passed to the C layer,
which keeps those fds open across `exec` while closing all others
(unless `close_fds=False`).

The POSIX `_communicate` uses `select.select` to multiplex stdin writes
with stdout and stderr reads. Mixing blocking reads on stdout with blocking
reads on stderr in two separate calls would deadlock when the child fills
the stderr pipe buffer while the parent is blocked reading from stdout. The
`select`-based loop interleaves writes and reads so neither pipe fills up.
On Windows the same problem is avoided by running two daemon threads, one
for each pipe, which drain concurrently into `BytesIO` buffers.

### `run`, `check_call`, `check_output` (lines 311 to 520)

<CpyLink path="Lib/subprocess.py" lines="311-520" />

```python
def run(*popenargs, input=None, capture_output=False,
        timeout=None, check=False, **kwargs):
    if capture_output:
        if kwargs.get('stdout') is not None or kwargs.get('stderr') is not None:
            raise ValueError(...)
        kwargs['stdout'] = PIPE
        kwargs['stderr'] = PIPE
    with Popen(*popenargs, **kwargs) as process:
        try:
            stdout, stderr = process.communicate(input, timeout=timeout)
        except TimeoutExpired as exc:
            process.kill()
            exc.stdout, exc.stderr = process.communicate()
            raise
        except:
            process.kill()
            raise
        retcode = process.poll()
        if check and retcode:
            raise CalledProcessError(retcode, process.args,
                                     stdout, stderr)
    return CompletedProcess(process.args, retcode, stdout, stderr)
```

`run` is the recommended high-level entry point for one-shot process
execution. `capture_output=True` is a shorthand for
`stdout=PIPE, stderr=PIPE`. On timeout, the process is killed and
`communicate` is called a second time to drain any buffered output before
re-raising `TimeoutExpired`. On any other exception the process is also
killed but the exception propagates without wrapping. This ensures the child
is never left running if the caller handles the exception.

`check_call` and `check_output` predate `run` and are kept only for
backwards compatibility. Both are implemented as thin calls to `run` with
`check=True`.
